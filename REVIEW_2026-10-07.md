# EOSIAL review and 3D feasibility — 7 October 2026

Scope: active JavaScript modules, application shell, pixel geometry, archive manifests and selected publication scripts. Application code and data were not changed. No updater, commit, push or deployment was run. This is code inspection and isolated logic validation, not a complete browser/security audit.

## Findings by priority

### 1. High: moving time presets can prevent external layers from rendering

References: js/layers/fire-hotspots.js:1078–1100,1293–1303,1955–1968.

getTimeRange() obtains a new current time on every call. FIRMS/S3 readiness uses exact start/end ISO timestamps. After loading, applyFilters() calls itself and computes a different key if the millisecond has advanced. This repeats archive checks rather than rendering. “All” also has a moving end time. Cached chunks may turn this into repeated promise work rather than repeated downloads.

Reproduction using the actual module with a controlled clock advancing 1 ms per call: 13 archive checks, 12 readiness keys, zero renders; deliberately stopped at check 13. Real scheduling may reuse the same millisecond, so behavior is timing-dependent.

Fix: resolve the interval once per user action/refresh and carry that snapshot through loading/rendering. Track chunk completion and in-flight loads; disregard superseded requests.

### 2. High: failed requests become apparently valid empty/partial results

References: js/layers/fire-hotspots.js:889–925,970–1060,1088–1094,1195–1207.

Recent-file failures return empty arrays, generally with console-only warnings. External archive failures mark the interval ready even when chunks are missing. A fixed custom interval cannot retry during the session. SFIDE also suppresses failed ranges and swallows its final fallback failure. Users can interpret a transport failure as fewer detections or no fires.

Fix: separate complete/partial/failed states, show dataset-specific warnings and a retry action, and disclose incomplete coverage in counts/exports. Mark completion only after necessary chunks succeed. Remove the hardcoded root-relative May 2026 FIRMS fallback.

### 3. Medium: MTG-FIR-only polygon queries cannot open results

References: js/layers/fire-hotspots.js:567,2214; js/app.js:786.

MTG-FIR intentionally has no FRP. queryPolygon() builds its table/animation but omits those detections from the numeric FRP series. The caller requires a nonempty FRP series to open results, so valid MTG-FIR-only selections fall through to “No active queryable layer.” Mixed queries undercount detections in the summary as well.

Reproduction: one MTG-FIR detection yielded zero series entries, one table row and one animation point.

Fix: open results based on detections, permit an empty FRP graph, and count all detections separately from those with FRP.

### 4. Medium: popup metadata enters HTML without escaping

Reference: js/layers/fire-hotspots.js:1469–1491.

Product, instrument, source label and raw confidence are concatenated into HTML. A test product containing an image with an event-handler attribute passed unchanged into the popup string. Hostile imported/published metadata can therefore introduce HTML/script injection. Browser script execution was not tested.

Fix: use textContent for metadata cells or consistently escape text fields; handle attributes/URLs separately. Audit generated satellite controls too.

### 5. Medium: invalid custom dates roll over silently

References: js/layers/fire-hotspots.js:1974–1998,1915–1922.

The main parser checks formatting but not component validity or start <= end. Reproductions: 31/02/2026 12:00 becomes 3 March; 07/10/2026 25:90 becomes 8 October at 02:30. The animation parser already checks components more strictly.

Fix: share one strict UTC parser and validate intervals before replacing the current selection.

### 6. Medium operational issue: public Nominatim used for autocomplete

Reference: js/app.js:135–167.

Typing triggers requests with a 400 ms debounce. The public service prohibits client-side autocomplete and limits requests to one per second. Older in-flight responses can also replace newer results.

Fix: use submitted searches with rate limiting/cache and stale-response protection, or an autocomplete-capable provider/self-hosted service. [Official policy](https://operations.osmfoundation.org/policies/nominatim/).

## Additional risks

- “All” downloads matching chunks concurrently and buffers whole FlatGeobuf files. Current manifests contain 492 FIRMS daily chunks, 456 Sentinel-3 daily chunks and 72 SFIDE chunks. Add bounded concurrency, progressive status, cancellation and a large-query policy. Memory exhaustion was not benchmarked.
- FIRMS/S3 publication copies directly over destinations, removes stale files and writes manifests/state directly. An interruption can leave inconsistent local outputs. Stage/validate data and replace atomically; prevent overlapping scheduled runs. GitHub Pages publication is separate from local writes.
- The active viewer loads data at startup without periodic reloading. A long-running tab does not acquire newly published detections automatically. Add refresh and a visible last-successful-update status.

## 3D feasibility

Feasible with a new renderer and tiled elevation. Leaflet currently owns map interaction, drawing and export. EV.pixelGrids.getHotspotFootprint() in js/layers/pixel-grids.js:112 already returns native MSG/MTG corners and approximate polar footprints, providing a useful geometry foundation.

My recommendation: retain Leaflet for 2D and lazy-load CesiumJS for an optional 3D view. Cesium supports ground-clamped GeoJSON polygons and hosted/self-hosted quantized-mesh terrain. Validate this choice with a small performance prototype. [Ground clamping](https://cesium.com/learn/cesiumjs/ref-doc/GeoJsonDataSource.html), [terrain provider](https://cesium.com/learn/cesiumjs/ref-doc/CesiumTerrainProvider.html).

MapLibre GL JS is another viable option for a pitched map of Italy using raster DEM terrain. A full migration would require replacing Leaflet drawing, clustering and capture behavior. [Official terrain example](https://maplibre.org/maplibre-gl-js/docs/examples/3d-terrain/).

| Elevation source resolution | Suggested use | Tradeoff |
| --- | --- | --- |
| 90 m | Regional/country prototype | Less storage/preparation; smoother relief |
| 30 m | Preferred visualization source | Better mountain/valley context; multiresolution tiles needed |
| 10 m or finer | Later, selected areas | More processing/storage; no improvement in fire-location accuracy |

Copernicus GLO-30 is a reasonable starting candidate; GLO-90 suits a coarse prototype. Copernicus DEM is a surface model including vegetation/buildings, not bare-earth terrain. Verify EEA-10 access/redistribution before selecting it. [Official collection](https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM).

Source resolution, rendered detail and fire-pixel size are separate. Prepare a terrain tile pyramid, verify the vertical datum and required height transformation, and document provenance. Measure storage before choosing hosting; separate terrain hosting may be preferable for this static site. Validate CORS, caching, attribution and tile availability.

Scientific requirements:

- Drape the whole footprint. Four elevated vertices alone create a flat facet that can intersect or float above mountains; use ground-clamped geometry or sufficient tessellation.
- Current polar footprints are north-aligned approximations using dimensions/area, without real swath orientation/corners. Keep their approximate status and prefer product corners when available.
- Terrain draping does not locate the burning fraction, sharpen fire pixels or correct geostationary parallax. Physical terrain-aware geolocation correction is a separate scientific task.
- Keep FRP attached to original detections; mesh subdivisions must not create detections or multiply FRP.
- Default exaggeration to 1, display any changed value, and maintain identical 2D/3D selection counts.

Proposed first increment:

1. Fix loading/time and detection-only query issues; expose shared filter state and selected-feature events independently of Leaflet.
2. Prototype one mountainous area with 30 m source elevation tiles, orbit/tilt, footprints, click metadata and synchronized filters. Convert current latitude/longitude corners to GeoJSON longitude/latitude and close rings.
3. Check 2D/3D corner agreement, steep slopes, tile edges, missing elevation cells, identical record counts/FRP totals and desktop/mobile performance.
4. Extend animation/export after renderer validation. Existing Leaflet/html2canvas capture requires dedicated WebGL handling.

## Validation and limits

All 11 JavaScript files parsed successfully with Node. Isolated execution of the actual hotspot module reproduced findings 1, 3, 4 and 5 using controlled clock/data/DOM substitutes. Other findings are code-path inspection and official service documentation. No browser automation package was available; layout, production CDN loading, WebGL, video export and performance remain unverified. Python/geospatial updaters were inspected but not executed.

## Fix implementation

The six numbered findings have been addressed in the working tree. Changes include snapshot-based filtering, protection against superseded requests, visible incomplete-coverage warnings/retry, detection-based result opening, escaped popup/control metadata, strict shared date parsing, and submitted/rate-limited/cached location searches. Archive downloads now have bounded concurrency and shared in-flight chunk requests. Browser validation also identified and fixed MTG-FIR comparison data incorrectly deselecting default SFIDE MSG satellites.

Focused Node regressions and a Chromium smoke check with synthetic data are included under tests/. The browser check covers startup, invalid dates, MTG-FIR table/animation, incomplete coverage, retry and mobile controls. The additional publication atomicity and periodic-refresh risks remain separate follow-up work; 3D is not implemented in this change.
